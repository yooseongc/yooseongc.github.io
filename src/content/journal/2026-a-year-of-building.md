# AI가 읽은 개발자의 1년 — 패킷 분석기에서 태블릿 알람까지

이 글은 2025년 11월 22일부터 2026년 11월 22일까지 yooseongc의 GitHub 커밋, 로컬 프로젝트, Codex 작업 기록을 바탕으로 AI가 정리한 회고다. 첫 두 달은 자료가 성기고, 2026년 2월부터 구체적인 구현과 검증 기록이 이어진다.

기록에서 가장 일관되게 나타난 특징은 **무엇을 만들든 마지막 시험을 실제 사용 환경으로 가져간다**는 점이다. Linux 바이너리는 다른 배포판에서 실행했고, 발표자료는 PowerPoint에서 열었으며, 3D 앱은 옆 창을 클릭한 뒤에도 카메라가 계속 움직이는지 확인했다. 반면 만든 뒤 몇 달 동안 얼마나 자주 썼는지는 기록이 드물다. 이 차이가 지난 1년의 작업을 읽는 실마리가 된다.

## 시기별로 본 개발 활동

| 시기 | 대표 작업 | 기록에서 확인되는 결과 |
|---|---|---|
| 2월 | INA Packet Analyzer, AliveHub | 패킷 원본은 PC에 두고 분석 결과 텍스트로 LLM에 질의하는 흐름을 구현했다. 별도 프로젝트에서는 두 노드와 시험 컨테이너를 함께 실행하는 고가용성 시험 구성을 병합했다. |
| 3월 | 네트워크 시뮬레이터, 커널·네트워크 학습 사이트, Coding Train | 화면에서 토폴로지를 그리고 L2·ARP 동작을 살펴보게 했다. 공통 코드 뷰어의 가로 스크롤을 고친 뒤 p5.js 학습 사이트의 서브모듈까지 갱신했다. |
| 4월 | psqlview, Taskboard | PostgreSQL 터미널 도구에 Vim식 치환 확인과 결과 셀 편집을 도입하고 1.0.0을 냈다. 협업 보드에서는 한 개발 라운드의 변경을 API 계약과 작업 절차, Claude 지침에 함께 반영했다. |
| 6~7월 | 폐쇄망 Docker 설치기, DeepCool 도구의 정적 빌드, 팀 세미나 자료 | Rocky Linux용 의존성 RPM을 준비하고, musl 바이너리를 Ubuntu에서 실행했다. Python으로 만든 슬라이드는 PowerPoint에서 글자 넘침을 검사했다. |
| 8~9월 | Windows 가상 카메라, Packet-IO | Windows 기본 카메라 앱과 레거시 앱에 맞춰 두 가지 출력을 제공했다. 패킷 검색 서비스는 API 계약과 Swagger 예시를 검증하고 RPM과 tar.gz로 배포했다. |
| 10~11월 | mimalloc 비교 실험, Envoy 실험실, 깨움, Vim 실습 사이트, 3D 월드, GBrain | 메모리 할당 성능과 TLS 협상 실패를 조사하는 한편, 실제 태블릿에서 쓸 알람과 브라우저에서 조작할 학습·감상 도구를 만들었다. 연말에는 여러 프로젝트의 작업 근거를 다시 찾을 수 있도록 GBrain에 연결했다. |

## 개발 스타일을 가장 잘 보여주는 두 건

**첫째는 실패가 발생한 구간을 좁히는 방식이다.** Envoy 실험에서 사용자가 볼 수 있는 증상은 HTTP 502였다. 작업 기록에는 그 앞뒤에서 무슨 일이 벌어졌는지가 남아 있다. 프록시가 원본 서버에 HTTP/2만 제안했고 원본이 TLS 협상을 종료했다. 두 구간이 독립적으로 협상하게 수정한 뒤, 앞 구간은 HTTP/2, 원본 구간은 HTTP/1.1로 연결되고 세 요청이 모두 200을 반환하는 것까지 확인했다. 나중에 같은 증상이 나와도 어느 구간부터 관찰할지 판단할 수 있는 기록이다. [Envoy 수정 릴리스](https://github.com/yooseongc/envoy-h2-lab/releases/tag/v1.4.1)

**둘째는 설명을 어디까지 믿을 수 있는지 표시하는 방식이다.** mimalloc 비교 실험에서는 256 KiB 할당 처리량이 약 40% 감소했다. 같은 요청 크기에서 페이지당 최대 객체 수가 15개에서 1개로 바뀐 것도 확인했다. 이 두 관찰은 페이지 관리 비용을 유력한 원인으로 지목할 근거가 된다. 다만 저하분 중 얼마가 그 변화 때문인지는 별도 A/B 실험이 필요하다고 남겼다. 앞의 Envoy 사례와 나란히 보면 차이가 분명하다. 하나는 수정 후 동일 요청이 성공했고, 다른 하나는 다음 실험에서 검증할 가설까지 도달했다.

## 관심사는 어디로 확장됐나

가장 뚜렷한 확장은 **도구를 사용하는 사람의 범위**에서 보인다. 패킷 분석기와 폐쇄망 설치기에서는 운영자가 가진 제약이 설계의 출발점이었다. Vim 학습 사이트에서는 320px 화면에서도 학습자가 미션 제목을 읽고 이동할 수 있는지가 중요해졌다. 3D 월드에서는 사용자가 화면을 보면서 옆 창을 조작하는 상황까지 재생 조건에 반영했다. 태블릿 알람에서는 잠금 화면과 알림 권한이 실제 기기에서 어떻게 작동하는지가 완료 기준이었다. 같은 해에 사용자 입장이 운영자에서 학습자, 관람자, 일상에서 알람을 쓰는 사람까지 넓어졌다.

**AI의 역할도 달라졌다.** 2월에는 AI가 패킷 분석 결과를 읽는 제품 기능으로 등장한다. 4월 Taskboard에서는 Claude가 다음 개발 라운드의 규칙을 읽을 수 있도록 문서를 갱신했다. 11월 GBrain에서는 새 채팅에서도 이전 프로젝트의 결정과 근거를 찾아갈 수 있게 했다. 이 흐름은 모델 선택보다 ‘다음 작업에 어떤 맥락을 건네는가’가 개발 과제로 자리 잡았음을 보여준다. 기록으로 생산성 향상률을 계산하거나 각 커밋을 특정 AI의 기여로 돌릴 수는 없다. [Taskboard 지침 정비 커밋](https://github.com/yooseongc/taskboard/commit/8843f00)

## 기록만 보고 경력을 추정한다면

가장 설득력 있는 추정은 **백엔드·네트워크 시스템을 개발하거나 운영 환경과 가까운 곳에서 문제를 다뤄 본 개발자**라는 것이다. 단서는 네트워크 저장소의 개수보다 여러 분야에서 반복한 선택에 있다. 인터넷이 끊긴 설치 환경을 전제로 재귀 의존성을 챙기고, 빌드한 바이너리를 다른 배포판으로 옮겨 실행하며, 프로토콜 협상을 구간별로 확인한다. 직접 통제할 수 없는 환경에서도 결과가 동작해야 했던 경험과 잘 맞는다. 공개 프로필에 적힌 백엔드·시스템·네트워크·인프라에 대한 관심도 이 해석과 일치한다. 구체적인 직함이나 연차, 어느 업무에서 익힌 습관인지는 이 자료로 특정하기 어렵다.

이번 분석에서 가장 궁금하게 남은 것은 **오래 살아남은 도구의 목록**이다. 어느 버전을 배포했고 어떤 환경에서 시험했는지는 자세히 복원할 수 있었다. 반면 석 달 뒤에도 알람을 매일 썼는지, psqlview를 어떤 작업에서 다시 열었는지, 세미나 생성 스크립트를 다음 발표에도 꺼냈는지는 알기 어렵다. 다음 회고에 ‘다시 사용한 날과 그 이유’가 더해지면, 이 개발자가 무엇을 만들 수 있는지를 넘어 어떤 문제가 꾸준히 시간을 들일 가치가 있었는지까지 읽을 수 있을 것이다.
